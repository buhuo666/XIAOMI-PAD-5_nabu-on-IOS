# GPU234：iPadOS CPU 调频

日期：2026-11-12，Asia/Shanghai。目标：iPadOS 全局实际 120fps、CA 总路径 <5ms、App 提交至 DPU 硬件接受 <8.32ms；全部 active，本轮尚未实机。

## 依据

GPU233 的 862 个精确关联输出：encoder_end CPU 与原始资源范围数线性（R²=0.989，约 147ns/条），draw CPU 与绘制次数线性（R²=0.9875，约 130µs/次）。同一 GPU232 去重收集函数在本机 Android 上按核绑定运行（18,688 条用例）：A55@1785.6MHz 约 46ns/条，A76@2419.2MHz 约 12.9ns/条，超大核@2956.8MHz 约 10.3ns/条；iPadOS 合成线程实测去重约 42ns/条、整段收集约 53ns/条。启动日志确认小核 0–3 已配对到 7/6/5/4 之后；内核没有 CPU 调频：hakios.cpufreq.c 使用别的 SoC 的 EPSS 地址且 cpufreq 未启用。Android 空闲时大核/超大核停在 710.4/825.6MHz。大核停在固件低频是与上述比值相符的解释，尚未在 iPadOS 内直接读到频率。

## 实现

`patches/nabu-power/NabuCpuFreq.h/.cpp`，`nabu-cpufreq=1` 启用（2 为全域锁高行）。寄存器来自本机 DT `qcom,clk-cpu-osm`：L3 0x18321000、小核 0x18323000、大核 0x18325800、超大核 0x18327800；布局按 Linux qcom-cpufreq-hw.c/osm-l3.c：LUT 0x110 起 32 字节一行，请求行 0x920（DCVS_CTRL bit0 置位时逐核），当前 vote 0x704。只写请求行，时钟源和电压由 OSM 自行切换。不请求高于本机 Android 上限的行（L3 1612.8、1785.6、2419.2、2956.8MHz），不使用少核 boost 行。

每 4ms 采样各核空闲时间：域内最忙核 ≥25% 立即升到高行，持续 1 秒 <10% 降到低行；大核与超大核共用一个需求，L3 随任一需求。TSENS0（0x0c263000，传感器 1–14，只读）每 200ms 取最热值：≥95°C 限到约三分之二频率行，≥105°C 限到低行，回落 10°C 解除（Android 被动阈值 110/125°C）。启动时记录各域 LUT、固件行和循环速度，之后每 5 秒记录请求/实际 vote/峰值占用/温度。

## 验证

主机 `NabuCpuFreqTest.cpp` 用本机 Android 频率表通过 ASan/UBSan（解码、逐核请求、需求、温度、整步）。ARM64 内核编译无警告；在 GPU226 对象集上替换 NabuDataKmod.o 并追加 NabuCpuFreq.o，共 66 对象，链接、实际分支、返回跟踪补丁和加载器窗口检查通过。启动包沿用 GPU233（含编码 CPU 汇总），仅内核和启动参数变化。

GPU 仍固定 675MHz；GPU 动态调频未实现。Turnip 命令流范围索引及 tile 重复转发修正未纳入本轮。状态：`log/host/gpu-v234/continuation.json`。

## 实机结果（GPU234–GPU238）

日期：2026-11-12。用户反馈：GPU234 起明显更流畅，但仍感觉不到 120Hz；GPU235/236/237 与各自前一轮相近，画面正常。全局实际 120fps 及两项延时目标仍为 active。

### 调频

- 固件留下的请求行：L3 第 13 行 1536MHz、小核第 15 行 1632MHz、大核第 0 行 710.4MHz、超大核第 0 行 825.6MHz。调频后请求 1612.8/1785.6/2419.2/2956.8MHz。
- 同一小核循环速度 407989→446387 次/ms，比值 1.094，等于 1785.6/1632。
- 合成线程的驱动去重 CPU：GPU233 为 41.9ns/条（1.076ms/25654 条），GPU236 为 12.9ns/条（0.623ms/48461 条），与 Android 上 A76@2419.2MHz 的 12.9ns/条一致。
- 0x704 回读恒为 4896000/2995200kHz，不随请求变化，不能作为实际频率的证据。
- GPU234–238 各轮最高温度 65.3/74.9/74.2/67.2/64.9°C，未触发限频。

### 结论与更正

- 编码计时本身有开销：GPU232 与 GPU233 每输出约 25.6k 条原始范围，render CPU 9.765→13.050ms。GPU236 起不再启用。
- 更正：此前把 endEncoding 开销归因于 tile 循环重复转发资源范围。GPU235 整屏直接渲染后原始/唯一范围比仍约 62 倍（87146211/1377177），tile 循环不是主因。源码中非 push 描述符集每次绑定都追加记录、提交时整集 resources 重复拷贝；这部分只体现在提交阶段收集约 0.8ms。
- 整屏直接渲染无收益：GPU236 与 GPU237 只差 TU_DEBUG=sysmem，按每输出原始范围分组的 GPU 均值（sysmem/默认）为 1–4 万 7.44/7.32ms、4–7 万 11.69/9.51ms、7 万以上 14.15/15.22ms。后续保持驱动默认。
- GPU 时钟未被欠频：GPU238 在 GX 上电后只读回读 gpu_cc_pll0 mode=d1000005（锁定）、L=70、alpha=0x5000，VCO 为 1350.0MHz；gx_gfx3d RCG cfg=0x101（源 1、分频 1），分支 0x4221（时钟开）；1350/2=675.0MHz，与请求一致。源 1 按厂商 gpucc-sm8150 取为 PLL0 二分频输出，未在此重新核对；只在上电后读一次，不是负载下采样。
- 剩余瓶颈：GPU 执行，典型桌面帧 CP→RB 约 8–10ms，约一半输出单这一段就超过 8.33ms；其次是重画面的合成 CPU，GPU236 的 378 个迟到帧对中 306 个 CA 串行超过 8.33ms。
