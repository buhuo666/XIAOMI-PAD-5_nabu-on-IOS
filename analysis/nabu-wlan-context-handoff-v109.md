# 第109轮：可恢复WLAN异常上下文递交链

2026-11-07，Asia/Shanghai。复用现用MPSS完整Hexagon反汇编；未改驱动、操作设备或重新审查固件。新增摘录在 `log/host/wireless-v108/wlan-context-followup/exception-consumer.asm`。以下地址是DSP静态地址，不是APPS可直接读取的地址。

## 本轮结论

v109继续保持WLAN运行基线。本次没有找到已闭合、值得加入本轮的主机诊断或修复。新证据把32字节异常记录接到了生成PFR的真实消费者，确认其中存在BADVA/LR，但该记录没有经已知PFR出口送到APPS。仅增加QuRT字符环读取或恢复旧DIAG握手候选仍不能保证获得它。

## QuRT递交和消费者

- `c08715b0`保存上下文指针、htid及周期计数；普通分支在`c087164c`调用`c08747a0`。
- `c0874888..48c4`把上下文对象链接到`c0875ccc`指向的队列，再调用`c0874610`。出队函数`c0874720`从该队列取首项，返回`r0=2/r1=对象指针`，另一队列返回3。
- `c0874610`检查`c0875cc0`保存的等待者；有待递交记录时，将事件/对象写到等待者`+0x90`，清除等待者槽，再唤醒线程。没有等待者时保持队列/优先级状态。
- 以上选定递交范围内没有对`c0872df4`或格式化器`c0874118`的调用。它是上下文移交，不是文本日志打印。更早的`c0841ea0`在特定条件下仍会回到`c086608c`的fatal分流，不能从该调用存在反推普通PDR必经fatal打印。
- 上述内核队列到QDI方法37内部实现之间还有调度/系统调用派发层，本次没有将所有中间间接目标逐一解析。下述用户态消费者的调用和数据流则直接可见。

根异常处理线程入口`c09a4d70`在`c09a4dac`调用`c09bcb5c`，提供栈上32字节记录。该包装通过`c0863a8c`调用QDI方法`0x25=37`，输出异常线程ID。公开同系头文件将37命名为`QDI_OS_EXCEPTION_WAIT`，与`qurt_exception_wait_ext`/`qurt_exception_wait2`的接口一致。

随后`c09a4de0/4df0`分别对故障线程和当前线程调用`c09bc61c`。该包装是QDI方法`0x4d=77`，同系头文件名称`QDI_OS_PROCESS_GET_ID`。两次查询成功且进程ID不同时，`c09a4e0c`调用`c0894504(故障进程ID, 故障线程ID, 32字节记录指针)`。

`c0894504`分配0x30字节对象：`+8`保存进程ID、`+0xc`保存线程ID，`+0x10`复制整份0x20字节记录。它在`c1b0b510`所指的链表中排队并置信号。消费者`c089449c`等到信号后取对象，在`c08944d8`调用`c0893d00(对象+8, 对象+0xc, 对象+0x10)`，随后释放该对象。不能把这一短生命周期队列当作停机后必然保留的固定转储区。

## PFR字段和异常记录

`c0893d00`先用进程ID查询进程名，再用线程ID的属性查询取得线程名。`c0893d94`组装的格式是现有`EX:%s:0x%x:%s:0x%x:PC=0x%x`。实参依次来自进程名、进程ID、线程名、线程ID、记录`+4`。

因此本轮已有PFR中的`0x1`是QuRT进程标识，`0x14b/0x14c`是异常线程标识；后者变化不能当作硬件错误码变化。该解释由原机参数数据流与同系QDI常量对照支持，而非由数字猜测。

32字节记录布局由公开`qurt_sysevent_error_t`和原机`c0892578`的SMEM格式实参共同校验：

| 偏移 | 字段 |
|---|---|
| +0x00 | thread_id |
| +0x04 | fault_pc |
| +0x08 | sp |
| +0x0c | badva |
| +0x10 | cause |
| +0x14 | ssr |
| +0x18 | fp |
| +0x1c | lr |

这些是布局证据，尚未取得本次记录的实际字节；不能把PFR数字填入cause，也没有实际BADVA/LR值。

## 现有其他出口为何不足

`c0893f94/3fa0`还检查用户PD注册的两个指针`+0x218/+0x21c`。满足条件后，非ERR_FATAL分支`c0894230..431c`通过QDI方法83向已注册用户崩溃对象复制故障PC、SP、BADVA、SSR、FP和LR。方法82/83在同系头文件中是`COPY_FROM_USER/COPY_TO_USER`，不是主机QMI请求。这里证明用户异常对象也是一个上下文保存点，但没有证明它在PD退出后保留、落在APPS共享区或有主机读取接口。

在`c0894320..4338`，已有DIAG消息仍只引用PFR字符串；`c08943c0/43c8`的两项PDR条件通过后，发送PFR并安排PD退出，跳过`c0894460`的SMEM611 writer。迄今没有在这条可恢复分支找到发出32字节寄存器记录的DIAG消息。该检索结论只覆盖上述已追踪范围，不是对全固件全部日志接口的否定。

## 下一步边界

1. 继续静态追踪用户崩溃对象注册和其已有导出者，或定位WLAN初始化前后的具体DIAG消息及描述符/SSID；只有证明出口携带所需上下文或能缩小实际故障阶段后，才设计对应主机采集。
2. 若后续通过受支持路径取得真实PD ELF或现成共享记录，先按PC和线程ID核对归属，再用上述32字节布局恢复BADVA/LR。该布局不能直接套用到TCB或任意内存偏移。
3. 本轮不增加签名固件修改、PDR→root fatal升级、调试安全位修改、未知MMIO读取、或只做DIAG协商的轮次。

公开头文件仅用于接口命名对照，不是Nabu固件原始源码。经项目代理一次下载并按C头文件审查，URL与Git blob标识保存在`wlan-context-followup/download.json`。重点是`qurt_qdi_constants.h:94/160`、`qurt_thread_context.h:39`和`qurt_event.h:89/292/320`；原机地址和实际参数流优先。


## 第109轮桌面验证期间补充：注册来源与主机出口

本段继续采用既有原件。新增LLVM18反汇编只覆盖`modem.b19`用户共享库的`0x18000..19000`和ULog创建函数`0x49494..49a34`；没有对全固件重新反编译。该库本身是嵌套ELF32 ET_DYN，其链接地址与外层modem的DSP装载VA是不同地址空间。以下不带`b/c`前缀的地址均是该嵌套ELF的相对VA。

### 两个注册指针来自用户共享库的BSS

`0x18740`分配0x800字节异常回调栈；`0x18760`加载`/dev/err_qdi_pd`（字符串相对VA`0x5b839`），`0x1877c`通过现有`qurt_qdi_qhi7`以QDI_OPEN方法2打开根驱动。传入r4/r5分别来自GOT`0x6f0a0/0x6f0a4`。两处原始RELATIVE重定位addend为`0x90b48/0x914b8`，均落在库的`.bss`相对范围`0x77000+0x270a8`。

根驱动`c0893b08`的OPEN分支创建0x230字节每客户对象，并在`c0893c78/7c`把这两个用户指针保存到`+0x218/+0x21c`。它没有把它们转换成SMEM对象，也没有提供APPS物理范围。外层只读PT_LOAD中的嵌套ELF载体，不含各用户进程运行时BSS的实际值。因此不应使用`外层b19基址+0x90b48`去读取此次崩溃。

此处理器明确分派的方法只有OPEN、`0x103`和`0x104`，其余进入默认QDI处理器。用户库`0x187ac/187cc`分别对应这两个私有方法；已读路径处理PDR标志及用户回调信息，没有返回异常记录的getter。`0x18a8c`取得回调信息、发给根端，执行已登记回调后通过`qurt_exception_raise_nonfatal`进入后续处理。它不是面向APPS的导出API。

结论仍是：**尚未找到受支持的主机取回32字节记录的出口**。现已闭合注册来源和生命周期，剩余缺口是一个真实跨DSP/APPS的日志或转储导出者。这个结论只覆盖已追踪的err QDI和回调路径，不宣称全固件不存在其它调试接口。

证据：`user-err-library.asm`、`root-err-registration.asm`、`user-err-registration-layout.json`。

### CCPM详细初始化打印属于本地ULog

`b0292c00`创建两个具名日志：`CCPM User LOG`大小0x1000、`CCPM User DEBUG LOG`大小0x400；两者创建参数memoryType均为`0x10301`。原机调用经`b0292c68`到`b0001a60`，重定位为`ULogCore_LogCreate`。打印包装`b02923fc`经`b0001a50`调用`ULogFront_RealTimePrintf`，而不是`msg_v2_send`。

同系`ULog.h:169`把`0x10301`定义为`ULOG_MEMORY_LOCAL`（local allocation + full access + local header）。固件中`Updating PLL lvalue`、`number of clocks`、`PLL lock status`、`Wait WSI_CMD`等详细记录由这一日志路径保存。头文件有库内`ULogCore_Read/Connect`声明，但没有因此得到主机QRTR读取口，也不能将“本地ULog存在”当作“F3 mask打开后会收到这些文本”。当前尚未定位可跨PD/主机读取这两个具名日志的具体协议。

证据：`wlan-ulog-and-conditional-diag.asm`、`user-ulog-create.asm`，以及已下载的`ULog.h`；有少数LLVM未解码指令的ULog创建内部路径未作行为结论。

- 若未来已有完整DIAG收发，可以按SSID4515和所需mask记录这组具体故障诊断；收到值才证明相应测试阶段执行。

- 这组描述符不足以独立支撑下一轮只增加DIAG握手。实际候选还缺可靠的双向流、对应动态PD ID/运行mask配置、完整报文解码，以及至少一个已知会执行的前置消息用来区分“未执行”和“日志链未通”。

本轮没有新的WLAN驱动候选。下一段可优先追踪`CCPM User LOG`的已有导出/注册协议；或沿正常初始化找到可形成明确前后顺序的DIAG消息，再结合已找到的SSID4515失败记录设计有判别力的采集。v110维持WLAN基线符合当前证据。
