## 已观察到的失败与恢复

第109轮从Android返回iPadOS后，单广告偏好精确域和有效域均保留false，原生
2005/200b/200c同一Reset区间内均status0，扫描正常。用户确认原耳机条目仍在，
但直接连接失败；也确认这副OPPO Enco Air5 Pro曾与同一平板的Android配对。

`log/device/nabu-boot-20261107-109/runtime-log/runtime.log`中的首次失败过程：

| 时间及行号 | 观察 |
|---|---|
| 12:25:32，33807–33811 | 远端触发SSP，收到IO Capability Request，OOB不可用 |
| 12:25:32，33827–33828 | 原生Link Key请求的查找成功，打印Found link key |
| 12:25:35，34024–34038 | 产生用户确认请求，发送给Preferences，建立本地配对计时器 |
| 12:25:38，34162–34165 | Preferences发送AcceptSSP，服务取消本地计时器并接受请求 |

因此不能把这次失败归为“用户一直没有确认”。同一秒还有SDP/L2CAP配置超时，
但不能仅凭先后日志将该超时判为SSP失败的根因。初始ACL已成功，失败发生在随后

用户随后在同次启动内重新配对成功，并将耳机放回盒中再取出，直接重连成功。

12:28:27 incoming ACL status0；12:28:29–30 A2DP、AVRCP、GATT、HFP均result0，
完成AAC-LC/44.1kHz协商。进程始终为PID62，期间未更换内核、bootstrap或蓝牙策略。
这证明同次启动的正常重连路径可工作；没有证明跨启动认证已通过，音频出声仍未验收。

## 705到158的原版映射

固定20F66的`0x1004d48bc`是`Pairing has completed with result`日志所在回调：

1. 输入w1保存在w19，日志格式明确是`bluetooth:OI_STATUS`。
2. 非零结果经`0x1004d4a28..4a30`传给`0x1003cab14`，w1=原OI状态，w2=10000。
3. 该映射函数对704..724使用跳转表`0x10067c520`。705对应index1，其字节为0x60；
   目标为`0x1003cab4c + 4*0x60 = 0x1003caccc`。
4. `0x1003caccc`直接返回`w0=0x9e=158`，随后调用上层失败处理。

这闭合了日志中705与158之间的映射关系，二者不是两次独立失败。当前没有读取
命名158的公开API枚举，不附加未经核实的枚举名称。

项目先前已观察HCI错误18→OI718、12→OI712。本次705与HCI0x05 Authentication
Failure的对应关系符合这一约定，但本次检查没有独立跟完底层事件解析器的全部
路径，也没有捕获失败时原始0x06/0x36事件字节，因此应区分OI日志与原始HCI采集。

已有Core5.4文档`log/host/wireless-v101/bluetooth-analysis/core54-hci.txt`的
Vol4 PartE §7.7.45明确：Simple Pairing Complete事件0x36在IO能力交换之外的SSP
序列失败时可统一使用Authentication Failure(0x05)。所以即使补获原始status5，
它也不能单独证明旧密钥不匹配；需要结合重配和切换系统的受控结果。

## Link Key查找入口及证据范围

`0x1004d4bd8`对应`Link key requested`/`Found link key`日志：先按设备地址取得
设备对象，再在`0x1004d4ce0`调用`0x1004d2034`查找缓存记录。成功后在
`0x1004d4cfc..4d10`将16字节记录及类型复制到返回结构，才打印Found日志。
`0x1004d2034`按设备地址在受锁保护的映射中查找；未找到时返回0x96。

因此Found日志有实际成功查找和复制分支依据，不只是蓝牙设置界面条目存在。
第109轮启动早期行3569还有`BTKCGetData ... returned 0`；没有读取该返回数据内容，
也未将该单条Keychain调用独自归属于耳机的BR/EDR记录。存储文件/Keychain查询到
此缓存的完整加载链尚未追完，不宣称所有密钥字段的持久化均已逐字节验证。

失败窗口的原生Found日志和重新配对后成功重连都说明不能直接采用“恢复缺失的
查找函数”或“无条件发送肯定回复”这样的修改；当前不改变任何认证结果。

## 第110轮的可证伪检查

两套系统共用同一控制器地址、各有独立配对记录，可能使耳机端现存记录与某一
系统不一致。这是合理候选，尚不是已证实根因；“曾经在Android配对过”本身也
不能证明第108→109轮期间Android实际发生过重新配对或改写耳机记录。

主任务已安排：本轮重新配对成功后将耳机留在盒中，返回Android并关闭蓝牙，
ADB已读回`bluetooth_on=0`，第110轮复用同一内核/bootstrap。结果尚待主任务记录。

- 若第110轮原配对直接连接成功，证明这组受控条件下跨启动配对可用，支持切换
  系统期间的外部状态影响；仍不能仅凭一次成功唯一归因于Android记录冲突。
- 若仍失败，应保留原记录，先确认首次连接有没有进入新的SSP及用户确认流程，
  再补有界的HCI事件类型/状态和Link Key肯定或否定回复opcode记录。只需记录
  0x17请求、0x040b/0x040c回复选择、0x06/0x36结果，不记录密钥或确认数值。
- 不能从“配对条目保留”推断认证完整成功；也不能从一次认证失败反推APFS丢失。

本轮没有提议更换MAC、共享两系统的密钥或绕过SSP确认。应先完成上述实机区分，
再决定是否需要有证据支持的持久化或双系统兼容改动。
